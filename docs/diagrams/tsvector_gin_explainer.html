Postgres full-text search: what tsvector and GIN actually do

The keyword ("sparse") half of CertCoach's hybrid retrieval, explained bottom-up

Step 1 — Raw text is useless for fast search

You store a chunk of text. To find "which chunks mention glacier pricing?", Postgres would have to read every single row and scan the text for those words. Fine for 10 rows. Terrible for 10 million.

Step 2 — to_tsvector() pre-processes text into searchable tokens

Postgres converts the text once, at write time, into a tsvector: a cleaned-up list of word-stems plus their positions. This is the fts column in CertCoach's schema.
Why stemming matters: a learner asking about "archiving" still matches a chunk that says "archival" — both stem to archiv. Why positions (:1 :2 :3) matter: they let the ranking function score chunks higher when your search words appear close together, not scattered across the chunk.

Step 3 — GIN flips it into an inverted index

GIN = Generalized Inverted Index. Instead of "row → its words", it stores "word → which rows contain it". Same flip as a book's index at the back: you don't read every page to find "Glacier", you look up the word and it tells you the page numbers.

Step 4 — Where this lives in CertCoach

A. Schema — migrations/001_chunks.sql. The fts column is generated: Postgres recomputes it automatically from content on every insert or update, so it can never drift out of sync with the text. 
CREATE TABLE chunks (
    id         BIGSERIAL PRIMARY KEY,
    tenant     TEXT NOT NULL,
    content    TEXT NOT NULL,                -- chunk text (Markdown)
    embedding  vector(1536),                   -- DENSE half  (meaning)
    fts        tsvector GENERATED ALWAYS AS    -- SPARSE half (keywords)
                   (to_tsvector('english', content)) STORED
);

-- dense index: approximate nearest neighbour on the embedding
CREATE INDEX chunks_embedding_ivfflat_idx
    ON chunks USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);

-- sparse index: inverted index on the tokenised text  ← THIS LINE
CREATE INDEX chunks_fts_gin_idx
    ON chunks USING gin (fts);
B. Query — backend/retrieval.py, sparse_search(). Two different things use fts here, and it's worth separating them: 
def sparse_search(conn, query_text, tenant, k=20):
    with conn.cursor() as cur:
        cur.execute(
            """
            SELECT id, tenant, content, ... ,
                   ts_rank_cd(fts, plainto_tsquery('english', %s)) AS score
            FROM chunks
            WHERE tenant = %s
              AND fts @@ plainto_tsquery('english', %s)
            ORDER BY score DESC
            LIMIT %s
            """,
            (query_text, tenant, query_text, k),
        )
        return [_row_to_chunk(row, row[11]) for row in cur.fetchall()]
PieceWhat it does
plainto_tsquery('english', ...) Runs the same tokenize + stem + stop-word pipeline on the user's question, so query words and stored words are directly comparable.
fts @@ plainto_tsquery(...) The match test: "does this row contain these tokens?" This is the part the GIN index accelerates — it narrows millions of rows to a handful.
ts_rank_cd(fts, ...) Scores the surviving rows using the recorded token positions — matches that sit close together score higher. Ranking, not filtering.
WHERE tenant = %s Multi-tenant isolation — an AWS query can never surface a GCP or Terraform chunk.
Division of labour: @@ + GIN answers "which rows are even candidates?" quickly. ts_rank_cd then answers "of those, which is best?". The index filters; the ranking function orders.

Step 5 — Why this sits next to the vector column instead of in Elasticsearch

Honesty note for interviews: ts_rank_cd is Postgres cover-density ranking, not true BM25 — it lacks BM25's IDF term-weighting and document-length normalisation. It fills the same architectural slot in a hybrid pipeline, so "BM25-style" is fair; claiming "we use BM25" would be overclaiming.
