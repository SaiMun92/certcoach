HNSW — Hierarchical Navigable Small World

Three ideas stacked: a small-world graph, greedy navigation, and a highway-style layer hierarchy

1. "Small world" — sparse graph, most links short, a few long

Every vector connects to only a few nearest neighbors (not all of them). A handful of long-range "shortcut" edges mean you can still cross the whole space in very few hops — the classic small-world effect.
vector node
local edge (near neighbors)
long-range shortcut edge

2. "Navigable" — greedy walk toward the query

Start anywhere, repeatedly jump to whichever connected neighbor is closest to the query, stop when no neighbor is closer than where you are. No global view of the graph is ever needed.
Each hop only ever looks at direct neighbors of the current node — never the whole graph. A long-range edge (dashed grey) lets step 2 skip most of the space in one jump; local edges then fine-tune the last stretch.

3. "Hierarchical" — layers act like highways → roads → streets

Layer 0 (bottom) holds every vector, densely connected. Each layer above keeps a shrinking random subset with sparser, longer-range connections. Search starts at the top and drops down one layer at a time, refining its position before descending.
Search order: enter at the top layer's single entry point → greedily walk (diagram 2's logic) using only that layer's sparse links → land at the closest node found → drop one layer down, keep that position as the new starting point → repeat the greedy walk with that layer's denser links → keep descending until layer 0, where the final walk lands on the true nearest neighbor(s).
The repeating pattern, per layer (this is the part to memorize)
  1. Greedy hop — at the current layer, jump node-to-node to whichever neighbor is closer to the query, until no neighbor is closer than where you are (this might take 1 hop or several — not a fixed number).
  2. Drop one layer — take that final position and descend exactly one layer down (never skip a layer, never jump back up).
  3. Repeat the greedy hop at the new layer — it's denser now, so this hop refines the answer further than the layer above could.
  4. Keep dropping one layer at a time, repeating steps 1–3, until you finish the greedy search at layer 0 — the densest layer, holding every vector — which gives the final answer.
In one sentence: start at the single entry point in the top (sparsest) layer, greedily hop neighbor-to-neighbor until stuck, drop one layer down, repeat the greedy hop with that layer's denser connections, keep dropping and refining layer by layer, until you finish the greedy search at layer 0 (which holds every vector) — landing on the actual nearest chunk.
Fewer nodes exist the higher you go, so early layers cover huge distances in very few hops (like a highway crossing a country). Each layer down narrows the search to a smaller neighborhood with more precision (arterial road, then local street) — so the total work stays roughly O(log N) instead of scanning all N vectors.

4. Worked example — a real CertCoach query

Same walk as diagram 3, but with actual chunk content instead of abstract dots. Query: "How is S3 Glacier priced compared to S3 Standard?" The corpus has ~300 chunks across 3 tenants (aws-saa, gcp-ace, terraform-assoc); only 5 are shown here for clarity.
What actually happens in CertCoach's code: the query gets embedded (embed() in backend/ai_client.py), then dense_search() in backend/retrieval.py asks pgvector for the nearest rows by cosine distance. If the corpus used an HNSW index instead of IVFFlat, this graph walk is what pgvector would do internally to answer that query — instead of the cluster-and-scan approach IVFFlat actually uses. Either way the chunk returned then goes through RRF fusion with the BM25/sparse results, then expand_chunks() pulls in its prev/next neighbors before it's handed to the LLM.
